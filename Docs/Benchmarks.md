# Benchmarks

Measured with `cd Tools && swift package benchmark` (package-benchmark, release
build). Every entry names the commit, machine and OS. Times are medians (p50).

## How to read the numbers

- **GMSetzer** has separate CommonMark and GFM entries. M2 now parses complete
  CommonMark blocks/inlines into a validated source-positioned tree. Historical
  M1 rows below measured block-only work. GFM rows before the M4 section
  measured CommonMark parsing with the GFM selection; from M4 they include
  all GFM extensions.
- **cmark-gfm (C)** has corresponding core and GFM entries. Both enable
  `CMARK_OPT_SOURCEPOS` for inline positions and include parser creation,
  parsing and freeing the document. The GFM entry attaches `table`, `tasklist`,
  `strikethrough`, `autolink` and `tagfilter`; extension registration happens
  outside timed iterations. Compare GMSetzer only with the matching entry:
  target **at most twice** its time, aiming for parity
  ([Plan, section 3](Plan.md#requirements)).
- **swift-markdown** includes its Swift tree construction and default parse
  options. The pinned 0.9.0 code enables smart punctuation and a fixed set of
  tables, strikethrough and task lists, without extended autolinks. It is a
  contextual app comparison, not an equivalent core/GFM speed reference.

The documents are generated by `Tools/Sources/BenchmarkCorpus`: a realistic
mix of headings, paragraphs with emphasis, links and code, lists, quotes, code
blocks, tables and non-Latin text, repeated up to the size.

### M1 containers

Quote/list continuation now uses an iterative open-container stack and a
single set of original-byte line views. The default depth ceiling is 128
container nodes (maximum configurable ceiling 256). Open leaf buffers remain
unique during continuation to avoid copying accumulated line indices on each
append. Source-cursor projection retains partial-tab provenance.

The Tools test/build also builds the benchmark executable against this API.
The 1,985-document C reference comparison checks behavior, not performance;
no new full benchmark run or speed claim is recorded here.

For the next measured entry, record the exact commit and dirty-state/diff,
Swift version, machine/OS, package lockfile, profile/options, actual UTF-8 byte

### M1 HTML and references

HTML start/end recognition uses byte scanners; leading reference definitions
are scanned through original paragraph ranges, without rebuilding or reparsing
an entire Markdown document. Exact reference metadata is opt-in. Production
HTML comment filtering and conformance rendering are separate paths, so future
measurements should distinguish parse, metadata and renderer options.

Both Tools comparison tests pass (1,985 exact-HTML and 1,924 block-structure
documents), and the benchmark executable builds. No full benchmark run, new
allocation figure or release speed claim was made for this change.

### M1-A correctness

Leading BOM handling preserves original offsets. Renderer wrappers share list
child scheduling with built-in rendering. Parsed custom leaves retain their
projected fallback literals in a sparse document table; `Node` and `NodeData`
do not grow. Built-in-only documents keep this table empty. Custom leaves pay
for literal construction and storage even when a caller replaces their HTML;
include that cost in the extension measurements before choosing storage changes.

The correctness tests and reference comparisons do not establish speed. No full
benchmark or new timing/allocation claim accompanies M1-A. M1-B must measure
the matching core/GFM references, actual UTF-8 byte counts, validation,
annotations off/on and rendering before accepting a phase budget.

### Block parser hot-path optimisation (branch `perf/block-parser-hot-paths`)

Six commits on top of `61fcb95` reduce work in the block parser without
changing its output or public API:

- `SourceCursor` no longer stores the source array, so it does not retain the
  snapshot every time a line is inspected.
- Open leaves record a contiguous line range instead of an index array.
- Container prefixes are matched without temporary arrays.
- Paragraph interruption, leaf starts and container openings check the first
  non-space byte before running a full scanner.
- Single source segments are stored inline (`SourceSegments`), and
  `Node.sourceSegments` stays a public array view.
- Validation reads node and token fields in place.
- A word-at-a-time scan finds line endings and the NUL check before decoding.
- Physical and projected lines share one table.
- Code, HTML and reference texts are copied as line slices and decoded once.
- Reference syntax tokens are emitted without temporary arrays.

**Measurement method (not a package-benchmark run).** A local release-build
harness parses the `mixed-v1` corpus and the reference corpus from
`Tools/Sources/BenchmarkCorpus`. It runs the parser 80 times per case and
interleaves the `61fcb95` baseline with the branch head in the same session.
Machine: Apple M2, macOS 27.0.1, Swift 6.4.2. Values are p50 in milliseconds.

| --- | ---: | ---: | ---: |
| CommonMark 100 KB | 2.08 | 0.66 | 3.1× |

| Selected GFM profile 1 MB | 21.0 | 6.7 | 3.1× |
| References 1 MB, syntax off | 20.9 | 8.1 | 2.6× |
| References 1 MB, syntax on | 26.3 | 9.4 | 2.8× |

not cover. Two owner-authorised filtered package-benchmark runs measured them
on the same Apple M2 host with
`swift package --package-path Tools benchmark run --target ParserBenchmarks
--filter "GMSetzer (position index|10k|outline|native analysis|editor snapshot|parent index|CommonMark parse).*"
--filter "Swift String UTF-16.*" --format markdown --time-units microseconds --no-progress`:
the [initial run](BenchmarkData/m3-services/initial-run.md) on merged `651af17`
and the [optimised run](BenchmarkData/m3-services/optimised-run.md) after the
service optimisations below. The `multibyte-v1` corpus is mostly non-ASCII
prose (CJK, Cyrillic, Hebrew, umlauts, emoji) so the ASCII fast path cannot
apply. Query cases use 10,000 evenly spread offsets per iteration. The editor
snapshot is parse + `DocumentIndex` + `SourceIndex` + outline + analysis with
all rules. Values are p50 in milliseconds.

| Case | 100 KB initial | 100 KB optimised | 1 MB initial | 1 MB optimised | 5 MB initial | 5 MB optimised |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| CommonMark parse (reference) | 2.697 | 2.728 | 28.033 | 27.607 | 147.456 | 148.898 |
| `SourceIndex`, mixed-v1 | 0.062 | 0.063 | 0.620 | 0.633 | 3.119 | 3.160 |
| `SourceIndex`, multibyte-v1 | 0.195 | 0.192 | 1.944 | 1.968 | 9.757 | 9.880 |
| Swift `String.utf16.count`, multibyte-v1 (context) | 0.195 | 0.200 | 1.977 | 2.019 | 9.765 | 10.166 |
| `DocumentIndex` | 0.076 | 0.081 | 1.000 | 0.786 | 17.744 | 6.611 |
| 10k position round trips | 4.911 | 2.290 | 5.415 | 2.888 | 5.693 | 3.084 |
| 10k caret queries | 0.899 | 0.921 | 1.300 | 1.332 | 2.863 | 2.922 |
| Outline | 0.034 | 0.031 | 0.333 | 0.317 | 1.952 | 2.439 † |
| Native analysis, all rules | 0.578 | 0.308 | 5.816 | 3.129 | 29.360 | 16.228 |
| Editor snapshot | 3.482 | 3.246 | 37.454 | 34.275 | 199.885 | 175.636 |

Parse timings match the M2 record (28.230 ms at 1 MB), so M3 adds no parse
cost. Queries allocate nothing; `SourceIndex` and `DocumentIndex` build with
three to four allocations at every size. At 1 MB the isolated services sum to
4.9 ms (analysis 3.1, `DocumentIndex` 0.8, `SourceIndex` 0.6, outline 0.3 ms);
the combined snapshot exceeds the parse by 6.7 ms (24%), as each service there
works on a freshly parsed, cache-cold document. The mixed corpus repeats its headings, so duplicate-heading
reports 3,648 findings per MB; finding construction dominates that rule.

Optimisations, each verified byte-identical against `275a69b` by the
differential probe over 2,958 documents:

- `DocumentIndex` reads nodes in index order when parents and earlier siblings
  precede each node (every builder append does), instead of chasing sibling
  links through 75 MB of 128-byte nodes at 5 MB; other layouts use the linked
  build. 5 MB drops from 17.7 to 6.6 ms.
- Position queries skip ASCII runs word-at-a-time from their checkpoint:
  round trips are 46–53% faster.
- Duplicate-heading keys of ASCII titles are collapsed byte-wise; other titles
  keep Character segmentation. Trailing-whitespace finds line ends with the
  shared SWAR `LineTerminators`, now a package type in `SetzerSyntax`.

† The optimised run included a traversal change that copied the node array
handle per step. A local release probe showed it slowed the 5 MB outline
(2.07 → 2.6 ms) without helping analysis, so it was reverted before commit;
the probe then measured 1.92–2.10 ms. The archived optimised export still
contains the reverted variant for outline and analysis; other cases do not use
the traversal.

## M5 raw front matter (development)

`feature/m5-front-matter` supplies an optional custom-block implementation.
Only the original document-start context can scan for a closing delimiter;
later candidate lines reject immediately, including after a dangling opener.
The extension preserves raw content without YAML/TOML deserialisation. Strict
CommonMark/GFM selections remain unchanged. No fresh benchmark series or
reference comparison was run; existing timings do not establish this step's
runtime or allocation cost. The large dangling-opener case is a functional
regression check, not a speed measurement.
