# Benchmarks

Measured with `cd Tools && swift package benchmark` (package-benchmark, release
build). Every entry names the commit, machine and OS. Times are medians (p50).

## How to read the numbers

- **GMSetzer** has separate CommonMark and GFM entries. M1 now parses leaf
  blocks and quote/list containers into a validated syntax tree with source ranges.
  HTML blocks and references are now included; inline markup and GFM rules are
  still pending. Do not compare its
  current timings as equivalent work to a complete parser.
- **cmark-gfm (C)** has corresponding core and GFM entries. Both enable
  `CMARK_OPT_SOURCEPOS` for inline positions and include parser creation,
  parsing and freeing the document. The GFM entry attaches `table`, `tasklist`,
  `strikethrough`, `autolink` and `tagfilter`; extension registration happens
  outside timed iterations. Compare GMSetzer only with the matching entry:
  target **at most twice** its time, aiming for parity
  ([Plan, section 3](Plan.md#requirements)).
- **swift-markdown** includes its Swift tree construction and default parse
  options. The pinned 0.9.0 code enables smart punctuation and a fixed set of
  tables, strikethrough and task lists, without extended autolinks. It is a
  contextual app comparison, not an equivalent core/GFM speed reference.

The documents are generated by `Tools/Sources/BenchmarkCorpus`: a realistic
mix of headings, paragraphs with emphasis, links and code, lists, quotes, code
blocks, tables and non-Latin text, repeated up to the size.

## Results

### 19 November 2026 – original M0 scaffold (historical configuration)

Recorded at `feature/m0-scaffold`; the original entry did not record an exact
measured commit hash. The historical harness is present in `2cdef7e`, but that
does not establish which revision produced the numbers. Machine: Apple M2, 8 cores,
16 GB, macOS 27 (Darwin 27.0.0).

| Document | GMSetzer (stub) | cmark-gfm (C, core) | swift-markdown | Historical 2 × C estimate |
| --- | --- | --- | --- | --- |
| 100 KB | 0.002 ms | 1.7 ms | 23 ms | ≤ 3.4 ms |
| 1 MB | 0.015 ms | 19 ms | 226 ms | ≤ 38 ms |
| 5 MB | 0.08 ms | 96 ms | 1,179 ms | ≤ 192 ms |

Allocations (total per parse): cmark-gfm (C) about 23 K / 224 K / 1,122 K;
swift-markdown about 66 K / 653 K / 3,267 K.

The GMSetzer stub only copies the text into a byte array; its numbers show
the cost of that copy, not of parsing.

### M0 review correction

The original C entry used `cmark_parse_document` with `CMARK_OPT_DEFAULT`,
without inline source-position tracking or GFM extensions. The benchmark
source now uses the two explicit configurations above. Its executable was
built during review, but no full benchmark run was performed. New timings,
allocations and enforceable ratio baselines remain pending; the historical
numbers must not be relabelled as measurements of the corrected harness.

### First M1 implementation

The parser now does real leaf-block work, source segmentation and tree
validation. The benchmark executable was rebuilt successfully against this
API. No full benchmark run has been performed; new release measurements remain
pending, and the historical stub timings describe neither this implementation
nor full CommonMark/GFM parsing.

### M1 containers

Quote/list continuation now uses an iterative open-container stack and a
single set of original-byte line views. The default depth ceiling is 128
container nodes (maximum configurable ceiling 256). Open leaf buffers remain
unique during continuation to avoid copying accumulated line indices on each
append. Source-cursor projection retains partial-tab provenance.

The Tools test/build also builds the benchmark executable against this API.
The 1,985-document C reference comparison checks behavior, not performance;
no new full benchmark run or speed claim is recorded here.

For the next measured entry, record the exact commit and dirty-state/diff,
Swift version, machine/OS, package lockfile, profile/options, actual UTF-8 byte
counts (the corpus rounds up to complete blocks), p50 and allocation metrics.

### M1 HTML and references

HTML start/end recognition uses byte scanners; leading reference definitions
are scanned through original paragraph ranges, without rebuilding or reparsing
an entire Markdown document. Exact reference metadata is opt-in. Production
HTML comment filtering and conformance rendering are separate paths, so future
measurements should distinguish parse, metadata and renderer options.

Both Tools comparison tests pass (1,985 exact-HTML and 1,924 block-structure
documents), and the benchmark executable builds. No full benchmark run, new
allocation figure or release speed claim was made for this change.

### M1-A correctness

Leading BOM handling preserves original offsets. Renderer wrappers share list
child scheduling with built-in rendering. Parsed custom leaves retain their
projected fallback literals in a sparse document table; `Node` and `NodeData`
do not grow. Built-in-only documents keep this table empty. Custom leaves pay
for literal construction and storage even when a caller replaces their HTML;
include that cost in the extension measurements before choosing storage changes.

The correctness tests and reference comparisons do not establish speed. No full
benchmark or new timing/allocation claim accompanies M1-A. M1-B must measure
the matching core/GFM references, actual UTF-8 byte counts, validation,
annotations off/on and rendering before accepting a phase budget.

### M1-B instrumentation

The harness now includes isolated tree validation and safe rendering, plus a
separate reference-heavy corpus with optional syntax collection off/on. The
original mixed corpus is unchanged. All 30 cases tag actual UTF-8 byte counts
and corpus identity and request allocation counts/bytes as well as wall-clock
percentiles. See [M1Measurements.md](M1Measurements.md) for comparison limits,
the run receipt and the local acceptance gate. This preparation supplies no new
timing results; the full run and data-based budgets remain pending.
