21 November 2026, owner-authorised execution on an existing Raspberry Pi 5
Model B Rev 1.0, four logical CPUs and 8,251,584 KiB reported RAM. Debian 13.7,
kernel 6.18.60+rpt-rpi-2712, glibc 2.41, Swift 6.4.2
(`swift-6.4.2-RELEASE`), toolchain Clang 21.0.0. This uses native hardware;
no VM/container, installation, power-setting or service change was made.

The source-only snapshot is clean commit
`c299783e7cac4783105f882db111905e6227e8d0` on `feature/m7-hardening`.
The isolated remote directory contains no Git checkout. All **121 transferred
file hashes** match before tests, before measurement and after completion;
all **48 runtime/benchmark hashes** match the earlier macOS baseline and the
local source. Runtime sources, dependencies, corpus inputs and limits are
unchanged. The [transfer manifest](../../BenchmarkData/m7-linux-arm64-2026-11-21/source-transfer.json)
records the archive hash and exact file scope; unrelated local configuration
and credentials were excluded.

### Measurement limits

This is a first Linux baseline at unchanged runtime code, not an optimization
or controlled cross-host speed claim. Reported load averages are high:
21.18 / 13.74 / 6.42 before, 13.78 / 12.68 / 8.71 after on four logical CPUs.
These include the cold-build history and do not identify concurrent work or
prove that it affected every sample. Other workloads were not managed;
frequency uses the existing `ondemand` governor. Temperature was 58.4 °C
before measurement and 48.5 °C at a later post-run check; thermal/frequency
state was not continuously monitored. Large cases have only 5–10 samples
per core parser/C case. Ratios describe this series; a repeat under observed
steady conditions is needed before tuning based on differences or claiming
a stable Linux performance envelope. No implementation change is justified
solely by these timings.

Allocator request counts and gross requested volume are retained with their
displayed labels/rounding in the CSV. Parser/C cases report positive values;
zero-allocation query cases retain their reported zeros. These are not
retained heap or peak RSS, and differing OS/toolchain allocator backends
preclude treating differences from the Mac as isolated code costs.

Swift emits startup warnings that it cannot protect swift-backtrace path/
environment and disables backtracing. The helper linker reports an RWX LOAD
segment; SwiftPM also emits native-build-system and legacy benchmark-package
warnings. They are retained in the logs; tests and the benchmark driver still
complete successfully. This run does not resolve those toolchain warnings.

With the existing Swift 6.4.2 toolchain selected in `PATH`, an isolated task
directory in `GMSETZER_TASK`, and the verified source snapshot as the current
directory, the executed commands have this shape (paths generalized):

```sh
export CLANG_MODULE_CACHE_PATH="$GMSETZER_TASK/module-cache"
export SWIFTPM_MODULECACHE_OVERRIDE="$GMSETZER_TASK/module-cache"
for gmsetzer_configuration in debug release; do
  swift test -c "$gmsetzer_configuration" --build-system native --jobs 2 \
    --disable-sandbox --scratch-path "$GMSETZER_TASK/build-$gmsetzer_configuration" \
    --cache-path "$GMSETZER_TASK/cache" --config-path "$GMSETZER_TASK/config" \
    --security-path "$GMSETZER_TASK/security"
done
python3 -I -m unittest discover -s Scripts
python3 -O -I -m unittest discover -s Scripts
swift package --package-path Tools --build-system native --jobs 2 \
  --scratch-path "$GMSETZER_TASK/build-bench" --cache-path "$GMSETZER_TASK/cache" \
  --config-path "$GMSETZER_TASK/config" --security-path "$GMSETZER_TASK/security" \
  --disable-sandbox --skip-update --force-resolved-versions -debug-info-format none \
  benchmark run --target ParserBenchmarks --format markdown \
  --time-units microseconds --no-progress
```

The same package command first runs `benchmark list --target ParserBenchmarks
--no-progress`, without the run-only format/unit arguments, to build and verify
the 72 identities. Preserve the owner-confirmation rule for another full run.
