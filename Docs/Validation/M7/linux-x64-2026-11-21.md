## Preparation correction and measurement isolation

The first list command exits 0, but its combined stdout/stderr lets a SwiftPM
deprecation warning split one case name. The identity guard stops before any
benchmark run. Repeating only the list command with separate streams verifies
all 72 identities; successful tests are preserved. The initial failed identity
check is retained in the [preparation receipt](../../BenchmarkData/m7-linux-x64-2026-11-21/preparation-status.json)
and archived streams rather than hidden or treated as a parser failure.

The subsequent SwiftPM-driven measurement shows an active competing caller:
over a 5.01-second process-counter interval, `swift-package` consumes
**251.78% CPU**, approximately 2.52 of the four cores, while its benchmark tool
is running. That incomplete measurement is cancelled before a complete export.

P50 milliseconds on identical `mixed-v1` input bytes, source positions on for
both parsers. GMSetzer includes construction, parsing/validated tree and
destruction; C includes corresponding parser/extension setup, parsing and
freeing. Compare matching CommonMark/GFM configurations.

| CommonMark | 1 MB | 1,000,100 | 44.990 | 33.718 | 1.334× | 111 / 148 | Pass |
| CommonMark | 5 MB | 5,000,500 | 231.342 | 144.835 | 1.597× | 22 / 35 | Pass |
| GFM | 100 KB | 100,284 | 4.854 | 4.538 | 1.070× | 1,019 / 1,089 | Pass |

| GFM | 5 MB | 5,000,500 | 282.329 | 271.843 | 1.039× | 18 / 19 | Pass |

For context, the C-based `swift-markdown` wrapper takes 13.083 / 140.640 /
718.275 ms at 100 KB / 1 MB / 5 MB. Its Swift tree construction, fixed feature
set and smart-punctuation defaults differ; it is not a matching core/GFM
reference and does not replace the direct C comparison.

All six [same-host relative checks](../../BenchmarkData/m7-linux-x64-2026-11-21/relative-budget.json)
pass. **Parity remains the goal** in Plan section 3; the 2× limit is a ceiling,
not evidence of parity. In this corpus/series, GFM is within about 7% of C
(1 MB is about 1% faster). CommonMark is **33–62% slower**; reaching the
corresponding C medians requires roughly **25–38% less GMSetzer elapsed time**.
CommonMark is therefore the next parser profiling priority. No timing alone
identifies a hot function or justifies removing validation/source information.

Apple-M2 absolute 10/60/300 ms deadlines and frozen M2 allowances/control drift
are not evaluated or relaxed for this Linux host. The separate historical Mac
series retains those checks. This is a first direct x64 baseline, not stable
performance acceptance across documents, hosts or architectures. Real selected
M5 processing and hostile-input scaling still need separate workloads.

## Observed conditions and limits

The [77 host samples](../../BenchmarkData/m7-linux-x64-2026-11-21/host-samples.jsonl)
and [derived summary](../../BenchmarkData/m7-linux-x64-2026-11-21/host-summary.json)
record five-second snapshots throughout the direct command. Aggregate CPU busy
time is **26.19%** across all four CPUs/all processes; iowait is **0.025%**.
One-minute load averages fall from about 6.01 to 1.00 as the preceding caller
activity ages out. The sampled thermal zone ranges **31–48 °C**, CPU0 frequency
0.8–3.88 GHz, minimum available memory 28,063,900 KiB, and free swap is unchanged
throughout. These snapshots do not prove absence of throttling or isolate
benchmark CPU time; CPU0 can be idle while another core runs the case.
Other owner workloads were not controlled or reconfigured.

Allocation request counts/gross requested volume retain their displayed labels
and rounding in the CSV. Core parser/C allocation values are positive; query
zeros remain zeros. These are not retained heap or peak RSS. Different OS,
toolchain and caller conditions prevent attributing cross-host differences to
CPU architecture or code changes alone. The x64 caller observation does not
quantify caller interference in the historical Mac/Pi series; verify their
driver conditions before using them for optimization attribution.

SwiftPM preparation emits deprecated-option/build-system and legacy benchmark
package warnings. Original combined test logs can contain interleaved warning
text; the passing final result lines/counts are intact. The direct benchmark
streams are separate. No warning is silently treated as a source/test failure.

## Reproduction and retained evidence

Library tests use native SwiftPM, two build jobs, separate Debug/Release
scratch paths, `--disable-sandbox` and task-local cache/config/security/module
paths, as in the [ARM64 reproduction](linux-arm64-2026-11-21.md#evidence-and-reproduction).
The tool suites add `--package-path Tools`, the corresponding `-c debug` or
`-c release`, `--skip-update --force-resolved-versions -debug-info-format none`;
their scratch paths are separate from the library and each other. Release
tools and benchmark preparation share the Release scratch directory. Python
commands are `python3 -I -m unittest discover -s Scripts` and the same with
`-O -I`.

The prepared/list command uses the same native Release scratch/cache options
as the ARM64 recipe, with stdout/stderr separated. Once all identities and
hashes are verified, the direct measurement command is (paths generalized):

```sh
# Directory containing the already built Release executables:
GMSETZER_BIN="$GMSETZER_TASK/build-bench/x86_64-unknown-linux-gnu/release"
"$GMSETZER_BIN/BenchmarkTool" --command run \
  --baseline-storage-path "$PWD/Tools" --format markdown --grouping benchmark \
  --benchmark-package-identifier package-benchmark --time-units microseconds \
  --no-progress --targets ParserBenchmarks \
  --benchmark-executable-paths "$GMSETZER_BIN/ParserBenchmarks" \
  > "$GMSETZER_TASK/benchmark.md" 2> "$GMSETZER_TASK/benchmark-build.log"
```

The current directory is the source snapshot root; keep source identity,
options and executable hashes with every run. Full-series/long-test execution
retains the existing owner-confirmation requirement.
