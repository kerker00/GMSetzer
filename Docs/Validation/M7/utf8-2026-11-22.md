22 November 2026, local candidate over `e3b4b0c`, identity `0.7.0-dev.1`.
One runtime file changes: `Sources/SetzerParser/InlinePhase.swift`.
Public API, grammar, source positions, Unicode replacement policy, limits,
protected fixtures, dependency pins and existing budgets remain unchanged.
This report describes an uncommitted candidate; receipts identify its source
hashes rather than claiming measurements of a clean candidate commit.

## Comparison contract

The historical `invalid-utf8-v1` input and its C control remain untouched.
That C control does not request UTF-8 validation. Even with validation enabled,
the pinned C parser and Swift differ on some malformed sequences: `c0 af`
produces one replacement character in C and two in Swift. Changing Swift's
standard-library replacement behavior to improve that comparison would change
the public contract.

The separate `UTF8Benchmarks` executable adds **36 cases**: three corpora,
16/64/256 KiB nominal sizes, and four variants (Swift syntax off/on, C UTF-8
validation off/on). Inputs retain complete units and tag actual byte counts.
The old corpus is joined by `invalid-compatible-v1` (invalid leading bytes,
NUL, truncated multibyte sequences and CRLF with matching replacement output)
and `valid-multibyte-v1` (German, emoji, Japanese and CRLF).

Two Release development tests establish deterministic bytes, exact HTML
agreement with validating C for the compatible/valid controls, annotation
invariance and the deliberate legacy difference, at 512/4,096/16,384 bytes.
The C bridge feeds original bytes without Swift repair and validates the C
HTML string rather than silently repairing that output. C options are
`CMARK_OPT_SOURCEPOS` with `CMARK_OPT_VALIDATE_UTF8` selected explicitly.
Both sides time parser construction, parsing and destruction; rendering is
outside these timed cases.

Matching repaired HTML is a better control, **not identical service work**:
Swift retains original malformed bytes and original byte coordinates, while
C source positions follow its normalized/repaired input. C's validation-off
rows are controls only. There is no general equivalent-work or C-parity claim.

## Profile and implementation

CPU/allocation profiles identify block text repair plus a second inline-phase
tree rebuild on plain text. The candidate reuses the already validated,
immutable block document only when it contains exactly one paragraph with
canonical physical node order, only text/soft-break children, no inline syntax
triggers, no custom inline rules and no document rendering policy to apply.
Reordered pre-transform storage still takes the normal rebuilding path.
Registered rule factories still run, and code-block info decoding is unaffected.
No document validation, Unicode repair or bounds checks are disabled.

Separate six-iteration allocation-stack exports for compatible malformed
256 KiB, syntax off, record:

| --- | ---: | ---: |
| Gross requested bytes | 52,475,775 | 24,636,098 |
| Allocation requests | 52,478 | 52,437 |

Gross byte traffic falls **53.05%** by removing redundant builder/emission and
child-index buffers. Repair still creates many small strings; request count
barely changes. These are requested totals, not retained heap or peak RSS.
Profiled timing is excluded. Failed CPU capture attempts remain separate from
the successful capture and contribute no measurement result.

## Unprofiled paired timing

Apple M2 / macOS 27.0.1 / Swift 6.4.2, Release `-O` and whole-module
optimization, direct built BenchmarkTool invocation without a SwiftPM parent.
Before/after runs each cover all 36 identities, with five-second sampling per
case, unchanged input bytes and source/executable hashes throughout each run.
No local build, tests or profiler competes during timing. Other owner activity,
power state and temperature are not controlled; this is a sequential pair,
not randomized repeated trials.

P50 milliseconds, nominal 256 KiB, Swift syntax off:

| Corpus | Swift before | Swift after | C validation-on before | C validation-on after |
| --- | ---: | ---: | ---: | ---: |
| Compatible malformed | 12.812 | 10.297 | 5.259 | 5.251 |
| Legacy malformed | 12.394 | 10.240 | 4.329 | 4.870 |
| Valid multibyte | 2.329 | 1.761 | 1.401 | 1.480 |

The compatible malformed case improves **19.63%**, with a stable validating C
control (−0.15%); Swift/C time changes **2.44× → 1.96×**. Syntax-on is
12.755 → 10.158 ms. The valid multibyte off case improves 24.39%, while the
legacy C control drifts 12.5%; do not generalize every isolated percentage.
The full comparison retains all 36 rows rather than selecting only wins.

## Evidence and remaining work

The [data directory](../../BenchmarkData/m7-utf8-2026-11-22/) retains original
before/after exports, comparison, CPU/allocation profiles including failed
capture attempts, test/sanitizer logs, full Mac exports/gates, hashes and the
candidate source overlay. Logs replace local home/task paths; the independent
public snapshot is compressed without modifying its serialized contents.

The current native x64 suites/tools, full x64 69/72-case refresh and fresh
42-case progressive resource matrix are tracked separately as they finish.
Minimum Swift 6.2 candidate CI and coverage-guided fuzzing remain required
evidence before an unqualified M7 completion claim. Existing historical
receipts retain their original source identities.

The parser already uses UTF-8 bytes, flat value nodes with integer links,
token arenas, reserved builder capacity and optimized compilation. Further
zero-copy work and a measured HTML byte writer remain opportunities. The
current renderer uses `String` accumulation; escape helpers reserve byte
buffers. Any future capacity hint must follow progressive render-group scope,
not eagerly reserve whole-document HTML for a requested small group. Input
size ×1.2–1.5 is only a heuristic: escaping, anchors and extensions can expand
output much further. No `-Ounchecked` or HTML-buffer refactor is introduced here.
